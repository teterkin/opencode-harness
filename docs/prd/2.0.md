# PRD: opencode-harness 2.0.0

**Goal** — сделать харнесс совместимым с opencode 2.x, зафиксировать 1.0.0 и
выпустить 2.0.0 с проверяемой версией, SemVer-дисциплиной и docs-baseline.

**Non-goals**

- Поддержка opencode 1.x: минимум — 2.3.0.
- Агент-оркестратор, OpenSpec-папки, метрики, отдельный docs-writer.
- Автоматические коммиты и релизы без подтверждения.

**User story** — Как пользователь харнесса, я хочу обновиться до opencode 2.x и
знать, что установленная конфигурация действительно подхватилась, чтобы не
ловить расхождения между README и реальностью.

**Acceptance criteria**

1. `tests/verify.sh` проверяет конфигурацию через HTTP API opencode 2.x и
   зелёный на 2.3.0.
2. `permissions` заданы ruleset-списком `{action, resource, effect}` в
   `opencode.json` и агентах; deprecated `permission` не используется.
3. `tests/doctor.sh` сравнивает версию с пином `opencode.version`, коды
   выхода: 0 — совпадает, 1 — ниже минимума, 2 — дрейф с запуском самотестов.
4. `install.sh` пишет манифест `harness-installed.txt`, `uninstall.sh`
   сносит по нему с fallback для установок 1.0.
5. `AGENTS.md` содержит правила v2: авто `git init`, ветки, SemVer, docs
   baseline, каркас проектного `AGENTS.md`, язык, doctor.
6. Есть команда `/release` и скилл `project-kit`.
7. `VERSION` = верх `CHANGELOG.md` = тег `vX.Y.Z`; это проверяется
   `tests/version.bats.sh`.
8. Docs-baseline на месте: `LICENSE`, `README.md`, `CHANGELOG.md`, `TODO.md`,
   `AGENTS.md`, `docs/prd/`, `docs/workflow.md`, `templates/`.
9. README идёт в порядке: описание, установка, использование, архитектура,
   версии и релизы.

**Open questions**

- Нужен ли `--dry-run` в `install.sh` — отложено до следующей версии.
- Есть ли смысл в проверке тега в `tests/run.sh` до релиза — сейчас тег
  проверяется режимом `--tag`.

**Sources and assumptions**

- Прочитано: `tests/verify.sh`, `tests/install.bats.sh`, `install.sh`,
  `uninstall.sh`, `agents/*.md`, `AGENTS.md`, `CHANGELOG.md`, `README.md`.
- Проверено на живом opencode 2.3.0: `/api/agent`, `/api/command`,
  `/api/skill`, `/api/config`; `permissions` в YAML-фронтматтере агента
  принимается.
- Допущение: `OPENCODE_CONFIG_DIR` не читается самим opencode, поэтому
  `install.bats.sh` использует его только для скриптов, а `verify.sh`
  проверяет живой конфиг.

**Risks**

- Миграция правил ломает существующие установки → `uninstall.sh` с fallback,
  бэкап конфига в `install.sh`.
- `install.sh` перезаписывает `model` и `default_agent` → на живой конфиг не
  запускается без согласия пользователя.
- `tests/verify.sh` зависит от экспериментального HTTP API → версия
  зафиксирована в `opencode.version`, дрейф ловится `doctor`.
