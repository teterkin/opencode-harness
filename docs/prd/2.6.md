# PRD: opencode-harness 2.6.0

**Goal** — метаданные репозитория (description, homepage, topics, visibility)
становятся частью docs-baseline: их заполняют при старте проекта и проверяют,
а не оставляют пустыми по умолчанию.

**Non-goals**

- Не автоматизировать `gh repo edit` в установщике харнесса.
- Не включать живую проверку в `run.sh`: она требует сети и `gh auth`.

**User story** — Как владелец проекта, я хочу, чтобы пустое описание и отсутствие
topics считались дефектом, а не нормой, и чтобы это было проверяемо.

**Источники**

- `gh repo view --json description,homepageUrl,repositoryTopics,visibility` до
  изменения: `description: ""`, `homepageUrl: ""`, `repositoryTopics: null`,
  `visibility: PUBLIC`.
- `skills/project-kit/SKILL.md` и правило 9 `AGENTS.md`: метаданные не
  упоминались ни разу.
- Формат topics из GitHub API: массив объектов с полем `name`.

**Acceptance criteria**

1. В `skills/project-kit/SKILL.md` есть раздел «Repository metadata» с четырьмя
   полями, правилами качества и командами `gh repo view` / `gh repo edit`.
2. Правило 9 `AGENTS.md` называет метаданные частью baseline.
3. `tests/repo-meta.sh` проверяет: непустой `description` до 350 символов без
   кавычек, 5–10 topics в нижнем регистре и kebab-case без дублей, `homepage`
   пустой или `https://`; коды выхода `0/1/2/3`.
4. Репозиторий заполнен: русское описание и 7 topics; `tests/repo-meta.sh`
   возвращает `0`.
5. `commands/release.md` требует прогонять `tests/repo-meta.sh` перед тегом.
6. `./tests/run.sh` зелёный, `tests/docs.bats.sh` проверяет формулировки.

**Risks**

- Живая проверка вне `run.sh` может отставать: topics поменяли, скрипт не
  запустили. Поэтому шаг добавлен в чек-лист релиза.
- Требование «5–10 topics» — эвристика: маленькому проекту может хватать трёх.
  Порог выбран как напоминание, а не как строгий стандарт GitHub.
