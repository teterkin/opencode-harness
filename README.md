# Харнесс совместной разработки для OpenCode

## Зачем нужен харнес

Модель сама по себе не знает, как устроена работа в твоей команде. Она пишет
код сразу, спорит с тестами, коммитит без спроса и считает зелёный прогон
доказательством, что всё в порядке. Не из вредности — просто задача звучала
именно так: «добавь экспорт CSV».

Харнесс решает это инструкциями, а не уговорами. Он кладёт в контекст каждой
сессии набор правил, разделяет работу между агентами с разными правами и даёт
короткие команды для типовых точек процесса.

Что меняется на практике:

- **План до кода.** Неоднозначная задача сначала превращается в PRD, и работа
  начинается только после твоего подтверждения.
- **Тест раньше реализации.** Агент показывает красный прогон перед тем, как
  написать хоть строчку production-кода.
- **Честная отчётность.** Модель обязана показать фактический вывод команды,
  а не сказать «тесты прошли». Если проверку выполнить нельзя — она так и
  пишет.
- **Ответственность за git.** Коммит, пуш, ребейз — только по прямой просьбе.
  `implementer` дополнительно не может переписывать историю: `reset`,
  `checkout`, `rebase` и `merge` запрещены на уровне permissions, а не только
  текстом.
- **Разделение ролей.** Планировщик физически не может редактировать файлы:
  `edit: deny` у агента `plan`. Ревьюер не может ничего изменить вовсе.

Чего харнесс **не** делает: он не заменяет тесты. Правило «сначала падающий
тест» живёт в тексте инструкций, и это всё ещё слово, а не проверка. Если
модель решит им пренебречь, единственная защита — ревью.

## Основные компоненты

| Компонент | Что это | Зачем нужен |
| --- | --- | --- |
| `AGENTS.md` | Инструкции, которые попадают в контекст каждой сессии | Правила, которые не зависят от того, какую команду ты вызвал |
| Скиллы (`skill/*/SKILL.md`) | Процедуры, подгружаемые по смыслу запроса | Длинные инструкции не висят в контексте всегда, а читаются, когда понадобились |
| Агенты (`agent/*.md`) | Роли с отдельными правами и промптами | Разные задачи требуют разных прав доступа |
| Команды (`command/*.md`) | Короткие точки входа: `/prd`, `/tdd`, `/review` | Не надо каждый раз объяснять процесс, достаточно одного слова |
| Permissions | Машинные правила доступа к инструментам | Единственная часть, которая действительно блокирует действие |
| Проектный `AGENTS.md` | Специфика репозитория | Команды сборки и тестов, структура, доменные инварианты — то, что невозможно угадать |

Как они соотносятся:

```
AGENTS.md          правила всегда в контексте
      │
      ├── agent/implementer   роль с правами: пишет код, историю не переписывает
      ├── agent/plan          роль без прав: только PRD, edit запрещён
      └── agent/reviewer      роль только на чтение: смотрит diff
                  │
                  ├── command/prd    → plan
                  ├── command/tdd    → implementer
                  └── command/review → implementer → reviewer

skill/tdd-workflow    процедура цикла, читается перед реализацией
skill/prd-authoring   шаблон PRD, читается перед планированием
```

Правила и скиллы пересекаются намеренно: в `AGENTS.md` — короткая версия
правила, в скилле — развёрнутая процедура. Короткое напоминание в контексте
плюс детали по запросу.

Репозиторий — источник правды, `~/.config/opencode/` — место применения.
`./install.sh` копирует файлы из репозитория в конфиг opencode.

## Что где лежит

### Глобальный уровень — действует во всех проектах

| Файл в репозитории | Куда устанавливается | Роль |
| --- | --- | --- |
| `AGENTS.md` | `~/.config/opencode/AGENTS.md` | Базовые правила. Попадают в контекст каждой сессии: TDD, PRD перед фичей, план до правок, атомарные изменения, реальная проверка, запрет git без спроса |
| `skills/tdd-workflow/SKILL.md` | `~/.config/opencode/skill/tdd-workflow/` | Строгий цикл red → green → refactor. Подгружается моделью перед написанием production-кода |
| `skills/prd-authoring/SKILL.md` | `~/.config/opencode/skill/prd-authoring/` | Шаблон PRD и правило «стоп, жди подтверждения» |
| `agents/implementer.md` | `~/.config/opencode/agent/implementer.md` | Агент по умолчанию (`default_agent`). Планирует, пишет тест, наблюдает red, делает минимум до green, проверяет |
| `agents/plan.md` | `~/.config/opencode/agent/plan.md` | Переопределяет встроенный `plan`. Только PRD или план, `edit: deny` |
| `agents/reviewer.md` | `~/.config/opencode/agent/reviewer.md` | Субагент-ревьюер. `edit: deny`, читает только `git diff/log/status` |
| `commands/prd.md` | `~/.config/opencode/command/prd.md` | `/prd <фича>` |
| `commands/tdd.md` | `~/.config/opencode/command/tdd.md` | `/tdd <задача>` |
| `commands/review.md` | `~/.config/opencode/command/review.md` | `/review` |
| `opencode.json` | `~/.config/opencode/opencode.json` | Модель, `default_agent`, базовые permissions. Накладывается поверх существующего конфига |

### Проектный уровень — действует только в репозитории

| Файл | Роль |
| --- | --- |
| `AGENTS.md` | Специфика проекта: стек, структура, реальные команды `test` / `lint` / `typecheck`, конвенции, доменные инварианты |
| `.opencode/agent/*.md` | Переопределения агентов под конкретный проект |
| `.opencode/command/*.md` | Проектные команды |
| `.opencode/skill/*/SKILL.md` | Проектные скиллы |

Проектные определения перекрывают глобальные (deep merge, проект побеждает).
Файл `AGENTS.md` нужно коммитить в git — тогда правила доезжают до всей команды.

### Структура репозитория

```
AGENTS.md                правила
opencode.json            модель и permissions
agents/                  implementer, plan, reviewer
commands/                prd, tdd, review
skills/                  tdd-workflow, prd-authoring
install.sh               поставить в ~/.config/opencode
uninstall.sh             снести, не трогая остальной конфиг
tests/run.sh             все проверки
```

## Требования

Установленный [opencode](https://opencode.ai). Харнесс настраивает именно его
конфиг, так что ставить его нужно заранее — при первом запуске, без него
`~/.config/opencode/` ещё пуст.

Документация и способы установки: <https://opencode.ai/docs/#install>

```bash
curl -fsSL https://opencode.ai/install | bash
```

## Установка

```bash
git clone <репозиторий> && cd harness
./install.sh
```

`install.sh`:

- создаёт `~/.config/opencode/`, если его нет
- кладёт правила, агентов, команды и скиллы
- **накладывает** `model`, `default_agent` и `permission` на существующий
  `opencode.json`, сохраняя `provider`, `mcp`, `plugin` и всё остальное —
  API-ключи не пропадают
- перед правкой сохраняет прежние файлы в `~/.config/opencode/backup-<дата>`
- валит установку с внятной ошибкой и ссылкой на документацию, если `opencode`
  не найден в `PATH`, и до этого ничего не пишет
- валит установку с внятной ошибкой, если `opencode.json` невалиден, и не
  трогает его
- идемпотентен: повторный запуск безопасен

Цель установки можно переопределить: `OPENCODE_CONFIG_DIR=/tmp/cfg ./install.sh`.

Снять харнесс, не потеряв провайдера и остальной конфиг:

```bash
./uninstall.sh
```

Конфиг читается только при старте — после установки выйди из opencode и
запусти заново.

### Проверки

```bash
./tests/run.sh
```

`install.bats.sh` проверяет установку и снос на временных каталогах: секреты
провайдера выживают, чужой `model` переопределяется, битый JSON валит
установку, повторные запуски безопасны. `verify.sh` проверяет, что текущая
настройка opencode действительно подхватилась — через `opencode debug`.

## Как ставить задачу

Задача — одна строка про **результат**, не про код. Не пересказывай правила:
они уже в `AGENTS.md`. Твоя часть — ответить на вопрос «что я хочу получить».

Четыре формы:

| Форма | Когда |
| --- | --- |
| Просто текст | Мелочь, всё однозначно. Агент сам поднимет цикл TDD |
| `/prd <фича>` | Непонятно, чего ты хочешь. Получишь PRD на утверждение |
| `/tdd <задача>` | PRD уже согласован, пора писать код |
| `/review` | Перед коммитом, после зелёного прогона |

### Не пиши решение вместо результата

Плохо — это описание реализации, модель не сможет предложить лучше:

```
Добавь функцию export_csv(), которая принимает список расходов и пишет файл
```

Хорошо — это желаемый результат:

```
Хочу выгружать расходы в CSV
```

Разница не в формулировке, а в свободе выбора: в первом случае модель
обязана сделать ровно это, во втором может предложить вариант лучше.

### Как отвечать на PRD

Развёрнутое ревью не нужно, хватит одной из трёх реакций:

- «да» — принимаешь как есть
- «нет, имя файла YYYY-MM-DD» — меняешь критерий
- «вопрос 2 не важен, решай сам» — снимаешь вопрос явно

Молчание согласием не считается: модель будет ждать ответа.

## Как пользоваться

Потренироваться стоит на отдельном приложении, не на рабочем:
<https://github.com/teterkin/expense-tracker> — небольшой трекер расходов,
на котором виден весь цикл от `/prd` до `/review`.

Агент `implementer` вызывается по умолчанию и сам держит цикл TDD. Каждый цикл
выглядит примерно так:

```
1. Какие команды нашёл: uv run pytest, uv run ruff check .
2. RED: написал tests/test_export.py
   FAILED test_writes_header_row
     E AssertionError: assert 'date,amount\n' == ''
3. GREEN: добавил write_csv
   58 passed
```

Если вместо этого увидишь «добавил функцию и тесты вместе» — харнесс не
сработал. Такой результат лучше не принимать, а разобраться в причине.

### Неоднозначная фича или большое изменение

```
/prd Добавить экспорт отчёта в CSV с фильтром по дате
```

Модель читает код, пишет PRD (цель, не-цели, история пользователя, критерии
приёмки, открытые вопросы, риски) и **останавливается**. Дальше — только после
твоего подтверждения. Открытые вопросы не выдумываются: неизвестное уходит в
список вопросов, а не в решение за тебя.

### Реализация

```
/tdd Добавить парсер CSV с заголовками на русском
```

Порядок работы:

1. Плана: какие реальные команды тестов и линта нашлись в репозитории.
2. **RED** — один падающий тест, запуск, показ фактического вывода.
3. **GREEN** — минимальное изменение, запуск, показ вывода.
4. **REFACTOR** — чистка под зелёным прогоном.

Красный тест должен падать по существу. Тест, который падает из-за опечатки
или неверного импорта, красным не считается.

### Ревью перед коммитом

```
/review
```

Ревьюер проверяет дифф на корректность, покрытие тестами (покрыто ли новое
поведение тестом, который без него упал бы), ослабленные или пропущенные
assertions, расползание скоупа, безопасность и риски. Ничего не коммитит.

### Переключение агента вручную

В TUI: `Tab` переключает агенты, либо укажи явно — «переключись на plan»,
«используй implementer». `plan` не может редактировать файлы, это by design.

## Правила, которые нельзя нарушить

1. **Нет production-кода без наблюдённого падающего теста.** Сначала красный
   прогон, потом зелёный. Тест и реализация не пишутся в одном шаге.
2. **Существующие assertions не ослабляются.** Не skip, не удалить, не
   закомментировать, не ослабить ради зелёного прогона — чинить код.
3. **Прав меньше.** Любое неоднозначное требование — сначала PRD, потом код.
4. **Одна задача — один дифф.** Без попутных рефакторингов и переименований.
5. **Проверки реальные.** Команды берутся из репозитория (package scripts,
   Makefile, pyproject, CI). Нет команды — так и сказать «проверить не смог»,
   а не делать вид, что всё зелёное.
6. **Git-операции только по явной просьбе.** `commit`, `push`, `reset`,
   `checkout`, `rebase`, `merge` запрещены без прямого указания в сообщении.
   В `implementer` `reset`, `checkout`, `rebase` и `merge` запрещены ещё и на
   уровне permissions, а `commit` и `push` остаются на одном слове.

## Настройка нового проекта

1. Запусти `/init` — команда просканирует репозиторий и создаст `AGENTS.md`
   с командами сборки/тестов, структурой и конвенциями.
2. Проверь, что команды в блоке `## Commands` действительно существуют.
   Всё, чего нет в репозитории, удали — иначе модель будет гонять несуществующие
   команды.
3. Добавь доменные инварианты в `## Domain notes`.
4. Закоммить `AGENTS.md` и `.opencode/` в git.

Приватные правила, которые не нужны коллегам, держи в
`~/.config/opencode/AGENTS.md` — он не коммитится.

## После изменений

Конфиг, агенты, команды и скиллы читаются один раз при старте и не
перезагружаются на лету. После правок — выйди из opencode и запусти заново.

Проверить, что всё подхватилось:

```bash
./tests/verify.sh
```

Или точечно:

```bash
opencode debug config      # валидный JSON, видны agent / command
opencode debug skill       # список доступных скиллов
opencode debug agent implementer   # промпт и правила конкретного агента
```

## Про модель и приватность

По умолчанию харнесс ставит `opencode/big-pickle`. Пока у этой модели
бесплатный период, входные данные могут использоваться для её улучшения. На
учебном проекте это безопасно, на рабочем — выбирай модель с zero-retention и
поменяй `model` в `opencode.json`, либо отредактируй свой
`~/.config/opencode/opencode.json` после установки: харнесс перезапишет
модель при следующем `./install.sh`.

## Если конфиг сломался

opencode не стартует при невалидном конфиге. Из уже запущенной сессии есть
аварийные входы:

```bash
OPENCODE_DISABLE_PROJECT_CONFIG=1   # игнорировать конфиг проекта
OPENCODE_CONFIG=/path/to/file.json  # подключить явный конфиг
OPENCODE_CONFIG_CONTENT='{"$schema":"https://opencode.ai/config.json"}'
OPENCODE_PURE=1                     # без внешних плагинов
```

Схема всех полей: <https://opencode.ai/config.json>

## Известные ограничения

- Правила в `AGENTS.md` — инструкции для модели, а не enforcement. Пермишенсы
  (`edit: deny` у `plan` и `reviewer`, `git reset*`, `git checkout*`,
  `git rebase*` и `git merge*` у `implementer`) реально блокируют действия;
  формулировки в тексте — нет. `git commit` и `git push` у `implementer`
  разрешены и держатся только на тексте.
- `default_agent: implementer` действует глобально. Скрипты и хуки, которые
  зовут встроенного агента по имени `build`, продолжат работать с ним, а не с
  `implementer`. Команды `/prd`, `/tdd`, `/review` явно указывают своего агента
  во frontmatter, поэтому на них это не влияет.
- Скиллы подгружаются по описанию, а не всегда. Если модель проигнорировала
  TDD-цикл — скажи «используй скилл tdd-workflow» явно.
